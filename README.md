# Hook Lab: варіанти скриптів для SockLock

Вебзастосунок для motion-дизайнерів SockLock. Дизайнер вставляє скрипт реклами-переможця і за 15–40 секунд отримує 10–30 варіантів хуків, перших фраз і тексту на екрані. Кожен варіант має тег кута подачі й автоматичні перевірки: схожість з уже протестованими хуками, довжину, ризики політики Meta. Дизайнер обирає потрібні варіанти й експортує бриф `.md` або CSV.

**Мета MVP:** скоротити текстову частину модифікації з ~1,5 год до ~0,5 год і зібрати дані для 2-тижневого пілоту.

---

## Як запустити

**Потрібно:** Node.js 20+ (перевірено на 24), npm і ключ Anthropic API з кредитами на балансі.

1. Встановіть залежності:
   ```bash
   npm install
   ```
2. Створіть у корені файл `.env.local`:
   ```
   ANTHROPIC_API_KEY=sk-ant-...
   APP_PASSCODE=спільний-пароль-команди
   # необов'язково, за замовчуванням claude-sonnet-5-5
   ANTHROPIC_MODEL=
   ```
   
3. Запустіть застосунок:
   ```bash
   npm run dev
   ```
4. Відкрийте http://localhost:3000, введіть passcode і виберіть **Demo script** → **Generate variants**. Демо-скрипти, гайд бренду й бібліотека хуків вбудовані, тож жодні файли не потрібні.

**Інші команди:**

| Команда | Що робить |
|---|---|
| `npx vitest run` | Юніт-тести: `similarity`, `checks`, `parseScript`, `csv` |
| `npx tsc --noEmit` | Перевірка типів |
| `npm run lint` | Лінтер |
| `npm run build` | Продакшн-збірка |

**Деплой на Vercel.** Імпортуйте репозиторій і додайте в Settings → Environment Variables `ANTHROPIC_API_KEY` і `APP_PASSCODE`. Команда отримає одне посилання й один passcode.

**Тестові дані** лежать у [`public/sample-data/`](public/sample-data/): 3 скрипти переможців, `brand-guide.md` і `tested-hooks.csv`.

## Як міряти успіх

### Головна метрика: час на текстову частину модифікації

| | Зараз | Ціль | Коли |
|---|---|---|---|
| Час на тексти однієї модифікації (хуки, перші фрази, текст на екрані) | ~1,5 год | **≤ 0,5 год** (−65%) | наприкінці 2-тижневого пілоту |
| Загальний час на модифікацію | ~3 год | ≤ 2 год | наприкінці пілоту |

**Як міряти:**
- **Базова лінія.** За тиждень до пілоту кожен дизайнер фіксує час на текстову частину 5–10 звичайних модифікацій (таймер або таймшит).
- **Пілот.** Застосунок пише лог кожного запуску: подію `generate`, вибір, правки, ↻ і `export` разом із секундами від генерації до експорту. Дизайнер окремо фіксує час, який пішов на доопрацювання тексту поза застосунком. Сума цих двох значень — це повний час на тексти.
- **Збір даних.** Наприкінці пілоту кожен учасник натискає **Log CSV** і надсилає файл.

### Пропускна здатність

| | Зараз | Ціль | Коли |
|---|---|---|---|
| Модифікацій на дизайнера на тиждень | базова лінія | **+40–50%** | 2 тижні пілоту |
| Модифікацій на місяць на команду | ~240 | ~350 після пілоту, **500** як ціль | 1–2 місяці після запуску |

Економія 1 год із 3 дає приблизно +50% пропускної здатності, тобто ~360 модифікацій на місяць. Щоб дійти до 500, треба прискорити й інші етапи модифікації. Тому пілот оцінюємо за першою цифрою.

### Корисність варіантів (з логу)

| Метрика | Ціль | Що показує |
|---|---|---|
| Частка запусків, що закінчились експортом | ≥ 80% | Варіанти взагалі придатні для роботи |
| Обраних хуків на запуск | ≥ 3 | Вистачає сильних варіантів |
| Частка обраних варіантів, які правили вручну | ≤ 50% | Якість тексту «з коробки» |
| Натискань ↻ на запуск | ≤ 5 | Модель рідко промахується |
| Частка обраних варіантів з 🔴 | ≤ 5% | Перевірки політики Meta працюють |

### Результат реклами (запізнілий показник)

| Метрика | Ціль | Коли |
|---|---|---|
| Hook rate (3-секундні перегляди / покази) модифікацій із застосунку | не гірше за історичні модифікації | 4–6 тижнів після запуску |
| Частка модифікацій, що стали новими переможцями | не гірше за історичну | 4–6 тижнів |
| Відхилення реклами модерацією Meta | не більше, ніж зараз | постійно |

Мета MVP — швидкість без втрати якості. Тому для рекламних метрик достатньо «не гірше», але відстежувати їх обов'язково.

### Вартість

Не більше $0.10 на модифікацію в API Anthropic. Поточна оцінка: ~$0.03–0.05 на генерацію, видно під кнопками експорту.

### Графік

| Тиждень | Що відбувається |
|---|---|
| 0 | Базова лінія часу, деплой, онбординг дизайнерів (15 хв) |
| 1–2 | Пілот: усі текстові модифікації через застосунок |
| 3 | Збір логів, порівняння з базовою лінією, рішення: розгортати чи доопрацьовувати |
| 4–8 | Результати реклами в Meta для модифікацій із пілоту |

**Критерій успіху пілоту:** час на тексти ≤ 0,5 год і ≥ 80% запусків закінчились експортом.

## Наступна ітерація

Пріоритет за впливом на пілот і мету 500 модифікацій.

1. **Центральне сховище логів.** Зараз лог зберігається в localStorage кожного браузера, і його треба збирати вручну. Варто відправляти події на сервер (Vercel KV, Postgres або Google Sheet), щоб метрики пілоту рахувались автоматично і нічого не губилось.
2. **Зворотний зв'язок з результатами Meta.** Імпорт CSV з Ads Manager → автоматичне оновлення бібліотеки протестованих хуків (winner/loser, ROMI) і статистика, які кути виграють. Тоді модель отримуватиме актуальні дані, а дизайнер бачитиме, з якого кута почати.
3. **Історія запусків.** Зараз результати зникають після перезавантаження. Треба зберігати запуски, щоб можна було повернутися до варіантів і повторно використати сильні.
4. **Стрімінг відповіді.** Показувати варіанти по мірі генерації замість 15–40 с очікування з порожнім екраном.
5. **Семантична схожість.** Триграми не бачать перефразувань («Your dryer steals socks» проти «The dryer is a sock thief»). Варто перейти на ембеддинги, щоб прапорці 🟡 і дедуплікація були точнішими.
6. **Доступ і витрати.** Особисті акаунти замість спільного passcode, щоб бачити, хто що генерує. Ліміт запитів і місячний ліміт витрат на API.
7. **Бриф у робочі інструменти.** Експорт у Google Docs або Notion і шаблони під формати (Reels 9:16, Feed 4:5) з урахуванням безпечних зон для тексту на екрані.
8. **Інші мови, коли з'явиться локалізація модифікацій.** Зараз основний ринок — США, і варіанти генеруються англійською. Коли SockLock почне локалізувати модифікації для інших ринків, треба додати:
   - **Мову чи ринок як окремий параметр запуску.** Він має потрапляти в бриф, CSV і лог, щоб метрики пілоту рахувались окремо для кожного ринку.
   - **Адаптацію замість перекладу.** Модель має писати хуки під культуру ринку, а не перекладати англійські. Для цього потрібен окремий гайд бренду для кожного ринку з місцевими «так звучимо» і «так не звучимо».
   - **Бібліотеку протестованих хуків для кожної мови.** Схожість з англійськими хуками для іншої мови нічого не показує.
